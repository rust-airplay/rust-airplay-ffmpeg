# 架构

本 crate 接住 `rust-airplay` 交出来的编码帧，把它变成一幅画面和一段声音。它是这对搭档里后端的那一半；
核心库仓库里的 [docs/BACKEND.zh-CN.md](https://github.com/rust-airplay/rust-airplay/blob/main/docs/BACKEND.zh-CN.md)
是它回答的契约。

## 两种媒体，两种形状

接收端停在编码帧上：一个音频载荷，或一个视频访问单元，在网络上加密、交出来之前已经解密。两者都不在这里解码，
核心库也不播放它们。

**视频是字节流。** H.264 和 HEVC 自带起始码与参数集，解码器能自己找到画面边界，不需要被告知边界在哪。帧按
push 的顺序写进程序的标准输入，投递到此为止。

**音频不是。** 裸 AAC-ELD 帧和裸 ALAC 帧没有同步字、自身也不带长度字段：唯一说明一帧在哪结束的是会话交给
我们的那个缓冲区，而字节流恰好丢掉了这条信息。核心库的 GStreamer 后端靠链接库、用 `appsrc` 每帧一个 buffer
解决。本后端做不到：它启动的是程序，程序读的是文件，不是一串 buffer。于是帧被包进一层容器，容器同时带着边界
和帧本身不携带的编解码配置。

## 一帧音频的路径

1. `AudioFrame { data, timestamp }` 到达 `push`。
2. `data` 变成一个 Matroska `SimpleBlock`：轨道号、毫秒偏移、这一帧的长度、以及帧本身。流打开时写一次的头部
   声明了轨道、它的编码（`A_AAC` 或 `A_ALAC`），以及解码器在读到第一帧之前必须知道的配置。BACKEND.md 专门
   提到这一点，所以配置在 `src/codec.rs` 里构造，而不是从流里读。
3. `timestamp` 数的是**采样**，不是秒：除以采样率才得到块里声明的毫秒。它只给块排序，不是时间表。
4. 字节写进 `ffmpeg -f matroska -i pipe:0 -f s16le ...` 的标准输入。
5. 从解码器标准输出出来的 PCM 按会话音量缩放，再写进 sink 的标准输入。

为什么是 Matroska 而不是 MP4：直播流只能往前写。Matroska 的 segment 和 cluster 都可以声明未知长度，于是没有
什么东西要在知道结尾之后回头补，读者也不必等一个完整的文件才能解第一个块。头部只有几百字节；块自带长度，而
这正是裸帧流缺少的那样东西。

## 一帧视频的路径

1. `VideoFrame { data, timestamp, keyframe }` 到达 `push`。
2. 如果调用方通过 `set_pace` 要过间隔，pacer 会把帧压到它在累积时间线上的截止时刻：每一帧的截止是上一帧的
   截止加一个间隔，所以一次睡过头不会把后面每一帧都往后推，而超过一个间隔的停顿是在当前时刻重新锚定，而不是
   用一阵突发送回来。
3. `data`——一个 Annex-B 访问单元，参数集已经在前面——按顺序写进 sink 的标准输入。

解码发生在 sink：默认是 `ffplay`，也可以是任何在自身参数前面接 `-f h264`（或 `-f hevc`）和 `-i pipe:0`
的程序。时间戳是客户端自己纪元的 NTP 定点数，不是这台机器的时钟，所以这里不拿它排程；接收端本来就会给流配速，
剩下的是管道的背压。

## 增益

`set_volume` 在任何客户端连上之前被调用一次，之后客户端每次拖动滑块都会再调用一次，而一个后端要做两件事：
作用在正在播放的流上，并记住给之后打开的流用。

音频之所以在这里解成 PCM、而不是交给解码器播放，原因就在这。写在解码器参数里的音量在进程启动时就固定了：要改
就得换进程，而换进程会丢掉队列、留下一段可听的空白。作用在路过 PCM 上的增益每采样一次乘法，在下一块就生效。
增益是一个装着 `f32` 位模式的 `AtomicU32`，由 renderer 和它打开的每条音频流共享，所以一次改变能在不持有锁
跨越 PCM 读的情况下到达正在播放的流。

值是线性幅度——`Volume::level`——作用在 16 位采样上时带四舍五入和限幅：大于一的增益会削顶，而不是把一个
响的采样绕回成安静的。

## 进程

每一级都是一个子进程。写线程让 push 在契约要求的意义上不阻塞：它排空一个四格深的队列，所以一个停止读取的
播放器会在两秒内变成一次被拒绝的帧，而不是一个永不返回的会话。关闭队列就是关闭管道，也就是程序需要的流结束。

程序说的话由它自己的线程排空，保留最后几 KB 在内存里。不写文件：后端不该被迫选一个路径，而那个文件恰好会在
流结束的那一刻被读。没人读的管道会填满并阻塞写它的程序，排空线程存在的理由就是这个。

每个程序有 150 毫秒说明自己被拒绝了，之后就当流已经开始，因为花时间的是进程启动而不是流打开。此后每个等待都
有期限：关闭时给程序五秒排空并退出，杀进程后两秒回收。

## Flush

flush 的意思是已经交出去的东西过期了。解码器和播放器都不能被告知忘掉已排队的内容，所以两者都换掉：

- 视频：换掉 sink 进程，pacer 的时间线重来。客户端的下一帧是关键帧，这才让新解码器正确而不只是空。
- 音频：两个进程都换掉，Matroska 头部重写一遍，流从客户端给的下一个时间戳重新开始。把 PCM 送到旧 sink 的
  泵线程不 join，让它自己读完那个即将关闭的管道结束。

## 失败

`Unavailable` 是环境：机器上没有这个程序、显示器打不开、FFmpeg 构建里没有这个输入格式。`Failed` 是请求：
程序拒绝了参数，或者在使用中停掉了。分类写在 `src/process/error.rs`，那里才有证据。

会话中途停掉的程序不会带走会话：下一次 push 报告它，接收端记录它，另一种媒体继续播。重试循环和静默重启都
不属于一个后端。

## 4K 镜像的延迟由编码决定

在同一台机器上、由 iPhone 发送、镜像里放秒表的实测：

| 广告 | 编码 | 结果 |
| --- | --- | --- |
| 3840x2160@60，只支持 H.264 | H.264 High，3108x2160 | **落后 1.48 秒**，流畅但慢 |
| 3840x2160@60，提供 HEVC | H.265，4K | 秒表量不出延迟 |

两行之间后端没有任何改动，只有接收端广告出去的编码不同：两边的每一级都很快（解码 185 fps、显示 178 fps、写入 0.1 ms、零丢帧，到达报告也显示窗口跟得上客户端自己的时间戳）。延迟在客户端 4K 的 H.264 镜像通路上，解决办法是把 HEVC 广告出去——`Config::features` 里置上 HEVC 位。支持 HEVC 的客户端会用 HEVC 编码镜像，画面就跟得上设备。

镜像变慢时，先看到达报告：它把客户端的时间戳和本机时钟放在一起，并给出每个窗口落后多少。它能区分"客户端追不上"（窗口在增长）和"客户端跟得上、是别处慢"（窗口持平）。

## 这里没有什么

- **音画同步。** 两种媒体带着两个不同时钟的时间戳到达。同时播放两者的后端得从它们建一条时间基，本后端不建：
  每条流由自己的程序、按那个程序读取的速率播放。
- **自己的窗口。** 显示器归 sink 管，本 crate 不画任何东西。
- **拖动。** sink 得到的是一条流，不是可以前后移动的文件；flush 是唯一改变播放位置的东西。
- **链接进来的解码器。** 没有 C 库、没有构建期的 FFmpeg、没有 `-sys` crate。代价就是本文开头那条：音频多一层
  容器，后端和编解码器之间多一道进程边界。
