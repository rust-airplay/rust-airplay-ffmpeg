# 性能

这里的每个数字都测自本后端开发所用的那台机器：Windows、32 线程的 Ryzen、Radeon 610M、PATH 上的 GStreamer 1.28 与 FFmpeg 8.1.1，iPhone 无线发送到有线主机。记录在此，是为了让"默认值该不该改"可以用测量而不是感觉来讨论。

## 镜像要达成的预算

4K 镜像以 3108×2160、60fps 到达，即每 16.7ms 一帧，后端要在这一帧内完成解码、缩放到窗口并呈现，还要留出余量给突发到达的帧。

| 工作 | 每帧耗时 | 60fps 下的余量 |
| --- | --- | --- |
| H.264 High 4K 软件解码 | 10.2 ms（98 fps） | 1.6× |
| HEVC 4K 软件解码 | 12.5 ms（80 fps） | 1.3× |
| 4K 解码 + 缩放到 1280×720 + 呈现 | 5.6~6.2 ms（160~180 fps） | 2.7× |

## 测过并且做了取舍的选项

| 设置 | 测量 | 采用 |
| --- | --- | --- |
| SDL 渲染器 | 1080p 30 帧：硬件 1059 ms vs 软件 778 ms；4K：152 vs 178 fps | 软件，通过 `Program::with_env` 传入 |
| 输入探测 | FFmpeg 默认 3401 ms 才开播；64 KiB 上限 259 ms | `-probesize 65536 -analyzeduration 0` |
| 解码线程 | 默认 168 fps，`-threads 8` 154 fps（4K HEVC） | 默认 |
| `-vf scale` 到窗口 | 155~177 fps，默认 160~180 fps | 不加：在噪声范围内，且强制缩放会让非 16:9 的手机画面变形 |
| `-hwaccel d3d11va` | H.264 108 vs 185 fps；HEVC 50 vs 80 fps（帧要下载回内存给 SDL） | 不用 |
| 墙钟时间戳 | `-use_wallclock_as_timestamps 1` 等价于 gst sink 的 `sync=false`：到达即显示 | 使用 |
| 热视频 sink | 冷启动 `video stream open in 94~315 ms`，而接收端的队列正是被这段启动期挤爆的 | `--warm-video` |

真正把测量延迟改变了一秒以上的，不在上表里：把 HEVC 广告出去，让 4K 镜像从**秒表上的 1.48 秒**变成秒表量不出的延迟，而上表每一级都没变。见 [ARCHITECTURE](ARCHITECTURE.zh-CN.md) 的编码一节。

## 播放时这个后端的开销

一次会话是四个进程：接收端、视频播放器、音频解码器、音频播放器。接收端每帧只做一次访问单元的移交和一次管道写入：到达报告显示 4K 60fps 下平均 0.1ms、最差 0.7ms，不到帧间隔的百分之一。

## 镜像变慢时看哪里

1. 到达报告里的 `raw <客户端时间戳> at <本机时间>`：帧到达时已经旧了多少；
2. 同一报告里的 `behind per window`：客户端是否跟得上；
3. 两者都正常，那延迟就在编码协商上——按实测，HEVC 与 H.264 的差别就在这里。
